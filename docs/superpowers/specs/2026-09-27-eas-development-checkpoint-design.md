# EAS Development Checkpoint Design

## Objective

Create an installable Android checkpoint build of DailyPilot through EAS Build. The APK must run without Expo Go or a local Metro server and must support Google/Supabase login, the deployed FastAPI API, chat, audio, tasks, memories, and the Google Calendar, Google Tasks, and Gmail connectors.

This checkpoint is for private development testing. It is not a Google Play production release and does not require a Play Console account or the Play closed-testing program.

## Selected Approach

Use an EAS internal-distribution preview build connected to the existing deployed services:

- Android package: `com.bharat948.dailypilot`
- App URL scheme: `dailypilot`
- Backend API: `https://dailypilotlab-2.onrender.com`
- Supabase: the existing project used by the app
- Google OAuth: the existing login and connector projects/clients

The build will use the existing backend and database. Testers must therefore use designated test accounts and avoid destructive tests against valuable data.

## Architecture

The EAS preview job compiles and signs an Android APK. Expo's Preview environment supplies the public client configuration that Metro embeds in the JavaScript bundle at build time.

The installed application communicates directly with Supabase for authentication and with the Render-hosted FastAPI service for application APIs. Connector authorization starts in the application, passes through Render and Google, returns to the Render callback endpoint, and finally deep-links into the installed application.

```text
EAS preview APK
  |-- Supabase Auth
  |     `-- dailypilot:// OAuth return
  |
  `-- https://dailypilotlab-2.onrender.com
        |-- authenticated application APIs
        `-- Google connector callbacks
              `-- dailypilot://connectors/callback
```

## Repository Configuration

### Expo application identity

Retain the existing package and scheme. Changing either could break signing continuity, Supabase redirects, or OAuth returns.

### EAS preview profile

Use one canonical `preview` profile with:

- `distribution: internal`
- `environment: preview`
- Android `buildType: apk`

Remove no production capability. The production profile continues producing an Android App Bundle for a future Play Store release. Redundant preview profiles may be removed if they have no distinct purpose.

### Client environment

Configure these values in the Expo project's Preview environment:

- `EXPO_PUBLIC_API_URL=https://dailypilotlab-2.onrender.com`
- `EXPO_PUBLIC_SUPABASE_URL`, copied from the corresponding value in the developer's ignored `app/.env`
- `EXPO_PUBLIC_SUPABASE_ANON_KEY`, copied from the corresponding value in the developer's ignored `app/.env`

All `EXPO_PUBLIC_*` values are compiled into the client and must be treated as public. Server secrets, OAuth client secrets, OpenAI keys, Supabase service-role keys, encryption keys, and database credentials must never be placed in this environment.

Local `.env` configuration remains available for LAN development and must not determine the remote preview build.

## Authentication Configuration

Supabase must allow the installed application's OAuth return URL. The allowlist must include the native `dailypilot://` return form generated by Expo AuthSession. Existing web and Expo Go development URLs can remain.

The login test must verify:

1. Google authorization opens from the APK.
2. Supabase processes the Google callback.
3. Android returns to DailyPilot through the custom scheme.
4. The app establishes and persists a Supabase session.
5. `GET /auth/profile` succeeds against Render.

## Connector Configuration

The Google Cloud OAuth Web client used by connectors must allow these exact redirect URIs:

- `https://dailypilotlab-2.onrender.com/connectors/google_calendar/callback`
- `https://dailypilotlab-2.onrender.com/connectors/google_tasks/callback`
- `https://dailypilotlab-2.onrender.com/connectors/gmail/callback`

Render must provide matching values for:

- `GOOGLE_CONNECTOR_REDIRECT_URI`
- `GOOGLE_TASKS_CONNECTOR_REDIRECT_URI`
- `GOOGLE_GMAIL_CONNECTOR_REDIRECT_URI`

The mobile client supplies `dailypilot://connectors/callback` as `return_to`. The backend stores that value with the OAuth state and redirects to it after exchanging the Google authorization code.

If the Google OAuth consent screen remains in Testing status, every person testing connectors must be registered as a Google Cloud test user. Calendar API, Tasks API, and Gmail API must be enabled for the OAuth project, and the configured scopes must match the app's consent-screen declarations.

## Render Considerations

Render is necessary for this shared checkpoint because a phone outside the developer's LAN cannot reach a laptop-only API. HTTPS also avoids Android cleartext-network restrictions.

The current deployment is reachable and publishes the expected authentication, chat, task, token, and connector paths. A free or sleeping Render instance may add cold-start latency. The app and test procedure must tolerate the first API request taking longer than normal; repeated unexpected timeouts remain defects.

## Error Handling

- Missing public client environment values must fail clearly during validation rather than silently falling back to `localhost`.
- Authentication cancellation must return the user to a usable login screen.
- Connector denial or failure must deep-link back to the connector screen with a visible error.
- Render cold starts must not be mistaken for an authentication failure without retrying.
- Expired Supabase or Google tokens must produce a reauthentication path rather than an application crash.

## Build and Distribution

The Expo account used for the build must own or have access to EAS project `3252f4f9-e2ed-4b83-b5e2-c8dd68076d4a`.

Build command:

```bash
cd app
npx eas-cli@latest build --platform android --profile preview
```

EAS may generate and manage the Android keystore on the first build. That credential must be retained for future builds of the same package.

The resulting EAS build URL can be opened on an Android phone to download and install the APK. The APK does not require Expo Go or a running Metro server.

## Verification Plan

### Automated checks

- TypeScript type-check succeeds.
- Expo configuration resolves successfully.
- EAS configuration resolves the preview profile and Preview environment.
- Render health and OpenAPI endpoints respond over HTTPS.
- Existing relevant server tests pass where they do not require unavailable external credentials.

### Device acceptance checks

1. Install or upgrade the APK and launch from a cold state.
2. Complete Google/Supabase login and onboarding.
3. Close and reopen the app; confirm session persistence.
4. Load the profile and settings from Render.
5. Send a text chat message and receive streamed output.
6. Record audio, upload it, and verify the response.
7. Create, update, complete, and delete a DailyPilot task.
8. Exercise memory and token-usage screens.
9. Connect Google Calendar and exercise allowed tools.
10. Connect Google Tasks, select a list, and exercise task operations.
11. Connect Gmail, read priority threads, create a draft, and test confirmed sending with a safe test message.
12. Disconnect and reconnect each connector.
13. Sign out, relaunch, and sign in again.

For each connector test, verify that both successful and denied consent return to the installed app.

## Out of Scope

- Google Play Console registration or submission
- The 14-day Play closed test
- Production store assets and policy declarations
- A separate staging Render or Supabase deployment
- EAS Update/over-the-air updates
- iOS distribution

## Completion Criteria

The checkpoint is complete when a signed preview APK can be installed from an EAS link and the device acceptance checks pass using the Render backend. Any dashboard-only prerequisites that cannot be changed from the repository must be documented with their exact required values and verified by the developer.
